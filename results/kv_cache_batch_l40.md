# 批量生成：KV cache 加速比随 batch 的变化（runs/ts_gpu_lr1e-3，设备 cuda）

贪心解码，prompt 4 个 token（取自验证集），每条生成 252 个，FP32，重复 3 次取中位数。吞吐 = batch × 生成 token 数 / 用时。

| batch | 不用缓存 tok/s | 用 KV cache tok/s | 加速比 | 两种方式结果不一致的条数 |
|---|---|---|---|---|
| 1 | 224 | 228 | 1.02× | 0/1 |
| 4 | 885 | 884 | 1.00× | 0/4 |
| 16 | 2,426 | 3,519 | 1.45× | 0/16 |
| 32 | 2,581 | 6,928 | 2.68× | 0/32 |
| 64 | 2,529 | 13,787 | 5.45× | 0/64 |
| 128 | 2,461 | 27,751 | 11.28× | 0/128 |

## 解读

- **不用缓存**：吞吐从 batch 16 开始就停在约 2,500 tok/s，不再随 batch 增长。每一步都要把整段（最多 256 个 token）× batch 重算一遍，
  batch 一大，GPU 就被这些重复计算占满了（计算瓶颈）。
- **用 KV cache**：吞吐几乎和 batch 成正比（batch 128 时 27,751 tok/s）。折算到每条序列约 217 tok/s，和 batch 1 时（228 tok/s）差不多，
  说明到 batch 128 为止，每一步的耗时仍然主要是固定开销（约 4.6 ms），每步只算 1 个新 token 的计算量远没有把 GPU 用满。
- **加速比随 batch 单调上升**：batch 1～4 约 1.0×，16 时 1.45×，32 时 2.68×，64 时 5.45×，128 时 11.28×。
  这验证了 `kv_cache_l40.md` 的诊断：KV cache 省下的是计算，只有当计算（而不是固定开销）成为瓶颈时，它才有明显收益。
- 所有 batch 下，两种方式生成的 token 完全一致（不一致条数都是 0）。
- 推论：用缓存时到 batch 128 都还是“开销瓶颈”，用 CUDA graphs 之类的办法降低每步的固定开销，还能让用缓存时的生成速度进一步提高。
