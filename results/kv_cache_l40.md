# KV cache 生成速度（runs/ts_gpu_lr1e-3，设备 cuda）

batch 1，贪心解码，prompt 4 个 token，FP32，重复 3 次取中位数。

| 生成 token 数 | 不用缓存 tok/s | 用 KV cache tok/s | 加速比 |
|---|---|---|---|
| 16 | 227.3 | 230.6 | 1.01× |
| 32 | 225.1 | 230.4 | 1.02× |
| 64 | 224.6 | 228.5 | 1.02× |
| 128 | 227.5 | 232.4 | 1.02× |
| 192 | 225.2 | 231.6 | 1.03× |
| 250 | 224.6 | 230.5 | 1.03× |

## 为什么几乎没有加速：batch 1 时瓶颈不在计算

同一个模型单次前向的耗时（GPU3，FP32，不编译，`no_grad`）：

| batch | 输入 1 个 token | 64 个 token | 256 个 token |
|---|---|---|---|
| 1 | 4.18 ms | 4.51 ms | 4.47 ms |
| 8 | 4.38 ms | 4.44 ms | 5.07 ms |
| 64 | 4.43 ms | 8.79 ms | 53.99 ms |

用 torch.profiler 看一次 batch 1、输入 1 个 token 的前向：一共启动了 253 个 CUDA kernel，GPU 真正在计算的时间只有 0.48 ms，
剩下约 3.7 ms（近 90%）花在 Python 执行和 kernel 启动上。所以 batch 1 时，不管输入 1 个还是 256 个 token，一步都要约 4.3 ms，
KV cache 省下的计算本来就只占很小一部分，生成速度被固定的开销卡在约 230 tok/s。

只有当每一步的计算量足够大时，KV cache 才有明显收益。从上表看，batch 64 时输入 256 个 token 要 54 ms，而只输入 1 个 token 是 4.4 ms，
差了约 12 倍：这才是 KV cache 能省下来的部分。
